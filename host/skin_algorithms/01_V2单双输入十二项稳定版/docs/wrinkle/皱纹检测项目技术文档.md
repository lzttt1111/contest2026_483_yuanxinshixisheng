# 皱纹检测项目技术文档

## 1. 项目概述

本项目是一个面向前端与运维对接的 Celery 异步算法 Worker，用于对单张正脸照片进行皱纹检测、规则后处理、医美分区分析和无监督量化。

整体链路如下：

1. 后端通过 Celery 向 `wrinkle` 队列投递任务。
2. Worker 根据 `oss_key` 从 OSS 下载输入图片。
3. `src.pipeline.Pipeline` 调用主算法程序执行皱纹检测。
4. 主算法输出最终叠加图、分区图、卡片图、CSV 量化表和 `summary.json`。
5. Worker 将本地结果文件上传回 OSS，并把 OSS key 返回给后端。

该系统用于图像分析、医美展示和算法工程辅助，不应作为独立医疗诊断、治疗指征或疗效承诺依据。

```text

```

关键文件说明：

- `src/worker.py`：Celery Worker 入口，负责接收任务、下载 OSS 图片、调用 Pipeline、上传结果。
- `src/pipeline.py`：算法调度层，负责检查输入、拼接模型路径、调用主算法程序、整理返回字段。
- `src/algorithms/wrinkle_detection_algorithm.py`：皱纹检测主程序，包含预处理、YOLO 推理、后处理、分区分析和输出保存。
- `models/best.pt`：Ultralytics YOLOv8 segmentation 皱纹分割权重。
- `models/face_landmarker.task`：MediaPipe FaceLandmarker 模型，用于 478 点人脸关键点检测。
- `models/selfie_multiclass.tflite`：MediaPipe ImageSegmenter 模型，用于 face-skin 语义皮肤分割。

## 3. 环境依赖

### 3.1 Python 运行环境

- Python：固定 CPython `3.10.20`
- uv：固定 `0.11.27`，以 `uv.lock` 为依赖版本、来源和哈希基准
- 默认运维环境：Ubuntu 24.04 LTS、x86_64、CPU
- 本地开发环境：Ubuntu 22.04 / WSL2
- Docker：只作为环境冲突时的兜底方案
- Worker 框架：Celery + Redis
- 存储：阿里云 OSS，通过 `oss2` 访问

### 3.2 Python 依赖

依赖在 `pyproject.toml` 中维护，核心依赖包括：

- `celery`：异步任务 worker。
- `redis`：Celery broker / backend。
- `oss2`：阿里云 OSS 下载和上传。
- `pydantic-settings`、`python-dotenv`：环境变量和 `.env` 配置读取。
- `numpy`：mask、坐标、矩阵和统计计算。
- `opencv-contrib-python`：图像读写、形态学、轮廓、骨架化和可视化。
- `torch`、`torchvision`：YOLO 推理底层张量计算，当前部署按 CPU 版安装。
- `ultralytics`：加载 `best.pt` 并执行 YOLOv8 segmentation 推理。
- `mediapipe`：新版 MediaPipe Tasks API，包含 FaceLandmarker 与 ImageSegmenter。
- `Pillow`：中文文字渲染，用于 `24_皱纹分区汇总图.jpg` 中的中文分区名称。
- `matplotlib`、`PyYAML`、`requests`、`psutil`、`polars`、`nvidia-ml-py`、`ultralytics-thop`：Ultralytics 及运行辅助依赖。

### 3.3 系统依赖

Dockerfile 已内置以下系统依赖：


说明：

- `libegl1`、`libgles2`、`libgl1`、`libglib2.0-0` 等用于 OpenCV / MediaPipe 在 Linux 环境中正常导入和运行。
- `ffmpeg` 用于 OpenCV 和图像处理相关编解码兼容。
- `fonts-noto-cjk` 用于中文字体渲染，避免分区卡片图中出现 `????`。
- `libgomp1` 用于部分深度学习和图像库的 OpenMP 运行支持。

### 3.4 为什么使用 CPU 版 PyTorch

当前 WSL 环境中 `nvidia-smi` 返回 GPU 访问被系统阻止，因此默认使用 CPU 推理。项目的 `pyproject.toml` 中配置了 PyTorch CPU wheel 源，避免 pip/uv 拉取 CUDA 轮子，减少镜像体积和部署不确定性。

如未来运维确认目标机器可用 NVIDIA GPU，可以在不改算法业务逻辑的前提下调整 PyTorch 安装源和 `.env` 中的 `WRINKLE_DEVICE`。

### 3.5 为什么使用 opencv-contrib-python

主程序在皱纹中心线生成时优先使用 `cv2.ximgproc.thinning` 做细线骨架化。该能力来自 OpenCV contrib 模块，因此依赖使用 `opencv-contrib-python`。如果该模块不可用，程序仍会回退到形态学骨架化，但 contrib 版本效果更稳定。

## 4. 配置项

配置来自 `.env`，模板见 `.env.example`。

基础服务配置：

```env
SERVICE_NAME=wrinkle
CELERY_BROKER_URL=redis://127.0.0.1:6379/0
CELERY_RESULT_BACKEND=redis://127.0.0.1:6379/1
OSS_ACCESS_KEY_ID=your-access-key-id
OSS_ACCESS_KEY_SECRET=your-access-key-secret
OSS_ENDPOINT=https://oss-cn-hangzhou.aliyuncs.com
OSS_BUCKET_NAME=your-bucket-name
OSS_RESULT_PREFIX=
```

皱纹检测配置：

```env
WRINKLE_RUN_PRESET=balanced
WRINKLE_CPU_THREADS=6
WRINKLE_DEVICE=auto
WRINKLE_OUTPUT_DIR=output
WRINKLE_SUBPROCESS_TIMEOUT=300
```

参数说明：

- `WRINKLE_RUN_PRESET`：运行预设，可选 `fast`、`balanced`、`full`。
- `WRINKLE_CPU_THREADS`：CPU 线程数，默认 6。
- `WRINKLE_DEVICE`：推理设备，默认 `auto`，当前一般自动落到 `cpu`。
- `WRINKLE_OUTPUT_DIR`：本地运行结果目录，默认 `output`。
- `WRINKLE_SUBPROCESS_TIMEOUT`：历史兼容配置；当前 Pipeline 已在 Worker 进程内直接调用算法，任务整体超时由 Celery `TASK_SOFT_TIME_LIMIT` / `TASK_TIME_LIMIT` 控制。

## 6. 从 0 到最终结果的算法流程

### 6.1 输入读取

主程序通过 `read_image()` 使用 `np.fromfile + cv2.imdecode` 读取图像，兼容 Linux UTF-8 路径和中文文件名。

输出图像通过 `cv2.imencode + tofile` 保存，同样兼容中文路径。

### 6.2 人脸关键点检测

程序调用 MediaPipe Tasks FaceLandmarker：

1. 加载 `models/face_landmarker.task`。
2. 使用 `vision.FaceLandmarkerOptions`，`running_mode=IMAGE`。
3. 对输入图片检测单张人脸。
4. 得到 478 个关键点，并按区域分组：
   - face oval
   - 左右眉毛
   - 左右眼睛
   - 鼻部
   - 嘴唇
   - 鼻孔下方区域

如果 FaceLandmarker 不可用或未检测到人脸，程序会直接停止，不退回整图推理。这样可以避免背景纹理被误识别成皱纹。

### 6.3 语义皮肤分割

程序调用 MediaPipe Tasks ImageSegmenter：

1. 加载 `models/selfie_multiclass.tflite`。
2. 输出 `category_mask`。
3. 取 face-skin 类别作为真实皮肤区域。
4. 对皮肤 mask 做小范围闭运算，填补小孔洞。

语义皮肤分割用于排除头发、背景、衣服和非皮肤区域，同时辅助后续额头区域补全。

### 6.4 人脸标准化预处理

主程序执行 `normalize_face_to_square()`：

1. 根据 FaceLandmarker 人脸轮廓生成基础人脸包络。
2. 结合 ImageSegmenter 的 face-skin mask 获取真实皮肤区域。
3. 对额头区域做补全，解决 FaceLandmarker 人脸椭圆在额头覆盖不足的问题。
4. 按人脸包络裁剪输入图像。
5. 将人脸放入黑底正方形画布。
6. 缩放到统一尺寸 `1024x1024`。
7. 同时保存：
   - 黑底分析图：用于 YOLO 推理。
   - 带背景展示图：用于最终可视化展示。

这一步让后续所有 YOLO 推理都在统一的人脸坐标系下执行，减少背景纹理误检。

### 6.5 构建推理视图

程序调用 `build_face_adaptive_views()` 构建多个 ROI：

- 整脸区域
- 额头区域
- 眼周区域
- 左眼区域
- 右眼区域
- 中下脸区域

`profile=extreme` 时会启用更多局部 ROI，提高浅纹召回。

### 6.6 图像增强与多尺度推理

每个 ROI 会根据运行预设生成不同增强版本：

- 原图
- CLAHE 柔和增强
- CLAHE 强增强
- 锐化
- 水平翻转

不同运行预设控制推理规模：

- `fast`：推理次数少，适合冒烟测试。
- `balanced`：速度和召回折中，日常推荐。
- `full`：最大召回，耗时更长。

YOLO 推理使用：

- 模型：`models/best.pt`
- 框架：Ultralytics YOLO
- 任务：segmentation
- 低置信度召回：`RAW_CONFIDENCE = 0.01`
- NMS IoU：`0.75`
- 最大检测数：`1000`

### 6.7 候选 mask 汇总

每次 YOLO 推理得到分割 mask 后，程序会：

1. 将局部 ROI 结果映射回 `1024x1024` 标准人脸坐标。
2. 去除局部裁剪边缘伪线。
3. 去除标准人脸 mask 之外的结果。
4. 合并所有候选 mask。
5. 统计每个像素被检出的投票次数。
6. 记录每个像素的最大分数。

输出包括：

- `01_第一阶段候选皱纹图.jpg`
- `06_皱纹投票热力图.jpg`

### 6.8 中心线骨架化

YOLO segmentation mask 通常较粗，不适合直接作为医美展示线条。

程序调用 `make_centerline()`：

1. 优先使用 `cv2.ximgproc.thinning` 做 Zhang-Suen 细化。
2. 如果 OpenCV contrib 不可用，则回退到形态学骨架化。
3. 删除过小连通域。
4. 得到细皱纹中心线。

这一步输出最终线条展示的基础结构。

### 6.9 人脸规则后处理

程序根据人脸关键点和皮肤 mask 构建多个禁止区和允许区：

- 眉毛及眉毛周边
- 眼球、睫毛、眼睑内部
- 嘴唇及唇缘
- 鼻梁、鼻翼、鼻孔阴影
- 鼻孔下方到上唇之间的人中/胡须区
- 脸缘、头发和背景交界处

然后对阶段 1 的候选线执行过滤，得到阶段 2 最终皱纹中心线。

输出包括：

- `08_最终皱纹检测图.jpg`
- `09_最终皱纹中心线.png`
- `12_人脸区域过滤调试图.jpg`
- `20_皮肤纹理参考图.png`
- `21_皱纹检测阶段对比图.jpg`

### 6.10 医美分区分析

程序调用 `build_aesthetic_region_masks()` 生成医美分区：

- 额头纹
- 眉间纹
- 左/右鱼尾纹
- 左/右眼下细纹
- 左/右法令纹
- 左/右木偶纹
- 其他纹

区域分配不是简单按固定框裁切，而是结合：

- 人脸关键点几何结构
- 皱纹连通域位置
- 区域吸附范围
- 额头纹与眉间纹方向判断
- 法令纹与木偶纹口角位置关系

这样可以减少边界区域皱纹被错误归类。

### 6.11 无监督量化

程序调用 `compute_region_metrics()` 计算每个区域的指标：

- `segment_count`：近似皱纹条数。
- `wrinkle_pixels`：中心线像素总长度。
- `mean_segment_length`：平均线段长度。
- `max_segment_length`：最长线段长度。
- `density_per_10k`：每 10000 像素区域内的皱纹密度。
- `share_pct`：该区域皱纹长度占全脸皱纹长度比例。
- `relative_score`：区域相对分数，按当前图片内最大区域归一化到 100。

这些指标是无监督相对量化，适合同一人前后对比、区域排序和展示，不等同于医学诊断分级。

### 6.12 中文可视化输出

`24_皱纹分区汇总图.jpg` 使用 Pillow + `fonts-noto-cjk` 渲染中文区域名，避免 OpenCV `cv2.putText` 不支持中文导致的 `????`。

## 8. 验收标准

一次任务成功的关键条件：

- 程序退出码为 0。
- `summary.json` 可被 JSON 正常解析。
- `region_analysis_status == "ok"`。
- `successful_runs > 0`。
- `failed_runs == 0`。
- `stage2_overlay`、`region_overlay`、`region_tiles` 图片可正常读取。
- `25_region_metrics.csv` 有表头和至少一行数据。
- `24_皱纹分区汇总图.jpg` 中中文区域名正常显示，不出现 `????`。

## 9. 运维部署注意事项

1. `.env` 中必须配置真实 Redis 和 OSS 参数，`.env` 不提交仓库。
2. `models/` 下三个模型文件必须存在，不能转换或改写。
3. Dockerfile 已包含 OpenCV、MediaPipe、Pillow 中文渲染所需系统库。
4. 输出目录 `output/` 是运行时产物，已在 `.gitignore` 中忽略。
5. OSS 上传时会保留原始扩展名，例如：
   - `region_tiles.jpg`
   - `region_metrics_csv.csv`
   - `summary_json.json`
   - `stage2_centerline.png`
6. 当前默认使用 CPU 推理；如后续接入 GPU，需要由运维确认宿主机驱动、容器运行时和 PyTorch CUDA wheel 配套。

## 10. 常见问题

### 10.1 MediaPipe 未检测到人脸

主程序会直接失败，不退回整图推理。这是为了避免背景纹理被误识别为皱纹。建议检查输入是否为清晰正脸图。

### 10.2 `24_皱纹分区汇总图.jpg` 中文乱码

确认系统已安装：

```bash
sudo apt-get install -y fonts-noto-cjk
```

Dockerfile 已包含该依赖。

### 10.3 OpenCV 导入失败

确认系统已安装：

```bash
sudo apt-get install -y libegl1 libgles2 libgl1 libglib2.0-0 libsm6 libxext6 libxrender1
```

Dockerfile 已包含这些依赖。

### 10.4 推理速度慢

可以将 `WRINKLE_RUN_PRESET` 调整为 `fast` 做快速预览。正式展示建议使用 `balanced`。

### 10.5 分区分析失败

查看 `summary.json` 中的 `region_analysis_status`，以及输出目录中的 `region_analysis_error.txt`。如果阶段 1、阶段 2 成功但分区失败，需要优先检查人脸关键点、区域 mask 和输出目录写权限。
