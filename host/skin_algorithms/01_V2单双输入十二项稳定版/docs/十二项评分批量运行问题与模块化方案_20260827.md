# DermaVision 十二项评分批量运行问题与模块化方案

> 更新日期：2026-08-27  
> 适用范围：`consumer`单 RGB 十二项本地批跑、旧九项到十二项评分 Bridge 及后续 38 万图长跑。  
> 本文是运行问题台账和工程方案，不改变 Worker 公开字段协议。

## 1. 2026-08-27 当前结论

- 评分批跑必须使用冻结 manifest，禁止递归枚举 38 万图库。
- 两个 slot 共用 claim 和断点，但各自保持常驻算法服务；当前上限固定为 2，禁止启动第三个 GPU 批跑 slot。
- 每张输入先暂存到 `/dev/shm` 或 Linux `/tmp`，校验大小和 JPEG 头尾后再供三套服务读取；不修改服务器原图。
- RTX 5060 Ti 双 slot 评分长跑的默认回收周期改为每 slot 8 张；15 张实测会在单周期内累积至约 15.1 GiB，不再作为本机正式值。
- Word 在评分批跑中关闭，输入图、十二项结果、衍生图、CSV、JSON、回执和评分 JSONL 保留。
- 严格 QC 是当前默认；人工放行必须写入独立 override JSONL，不修改原始结果。
- 整图 QC `REJECT` 不进入任何正式评分拟合；单算法失败或单模块有效面积为 0 时，只排除对应模块，其他可评估模块继续入组。
- 不可评估必须保存为 `null`，不得写成 0 分或0目标，避免把“缺少证据”误解为“没有问题”。

## 2. 评分样本资格合同

| 运行结果 | 整图是否入组 | 模块处理 |
|---|---|---|
| `success` 且 12/12 | 是 | 各模块按自身证据入组 |
| `partial_success`，单算法失败，整图非 REJECT | 是 | 失败模块不入组，其他模块继续 |
| 单模块有效面积为 0/分区不可评估 | 是 | 该模块输出 `null`，不进入该项 ECDF |
| `partial_success`，`input_quality_reject` | 否 | 整图归档人工复核 |
| `failed` | 否 | 根据错误类别决定是否可重试 |
| 人工明确放行的严格 QC 样本 | 是 | 以 override 作为最新终态，保留原 QC 证据 |

该合同由两层保证：

1. `src/nine_analysis/v2_proxy_projection.py` 按模块保留可评估指标。
2. `src/scoring_bridge/builder.py` 允许非整图 REJECT 的算法级 partial 进入 Bridge，再由各维度评分器跳过空模块。

## 3. 本次批跑问题台账

### 3.1 禁止扫描 38 万图库

- **现象**：递归 `find`/`du`/`ls -R` 会让 NFS、WSL 和 D 盘长时间满载。
- **根因**：在网络文件系统上枚举海量目录项，诊断命令本身就会制造 I/O 压力。
- **解决**：从旧评分 JSONL 冻结相对路径 manifest，`--input-manifest` 只读明确路径，服务器目录枚举次数为 0。
- **防复发**：manifest 模式禁止回退到目录扫描；测试必须断言不调用递归枚举。

### 3.2 NFS 短读、JPEG 缺失 EOI

- **现象**：长跑中偶发解码不完整，同一图重试又恢复。
- **根因**：多服务同时直读 NFS 原图，网络短读被误当成完整输入。
- **解决**：每图只复制一份到 Linux 临时盘，校验文件大小、JPEG SOI/EOI；仅对临时副本补缺失 EOI。
- **防复发**：三服务必须共用已校验副本，禁止各自复制或修改服务器原图。

### 3.3 WSL/VmmemWSL 内存长时间不回落

- **现象**：Windows 看到 VmmemWSL 接近 32 GiB 上限，但 Linux 进程 RSS 之和明显更低。
- **根因**：常驻服务内存、Linux 页缓存和 WSL 已提交内存叠加；Windows 任务管理器不等于 Linux 实际活跃 RSS。
- **解决**：启动前检查 available/swap，本机双 slot 长跑每 8 张受控回收服务；需要时先 `sync`，再从 WSL 回收页缓存和请求 compact memory。
- **防复发**：启动门设为可用内存至少 16 GiB，运行中硬门为 4 GiB，Swap 上限 6 GiB。不在任务运行中执行 `wsl --shutdown`。

### 3.4 GPU 双 slot 与冷启动认知偏差

- **现象**：双 slot 后显存高于单 slot，容易误以为“同一套 GPU 服务被两进程零成本共享”。
- **根因**：当前 slot 是两个独立 Python 进程，CUDA 上下文和模型内存不能在两进程中无拷贝共享。
- **解决**：双 slot 各自冷启动一次，然后持续处理；共享 claim 避免重复图，每 15 张回收。
- **实测**：本次冷启动约 9.2 秒/slot，热态单 slot 约 21–24 秒/图，双 slot 唯一图有效吞吐约 11–12 秒/图；显存常见约 9.6–11.1 GiB。
- **防复发**：`MAX_SHARED_GPU_WORKERS=2`，第三 slot 失败关闭；不以牺牲结果为代价追求并发。

### 3.5 D 盘 100% 活动时间

- **现象**：机械 D 盘出现长时间 100% 活动，系统卡顿。
- **根因**：输入扫描、多服务临时图、正式结果及 Windows 页面文件争抢同一机械盘。
- **解决**：临时现场固定在 `/dev/shm`或 Linux `/tmp`；D 盘仅串行发布正式结果，通过 `_export.lock` 避免两 slot 同时大批写入。
- **防复发**：禁止将 Word、模型缓存和调试中间图加入评分长跑；监控 D 盘延迟而非只看瞬时带宽。

### 3.6 claim 遗留和中断恢复

- **现象**：热更新或 Ctrl+C 后，个别 `.lock` 目录保留，样本被误判定为正在处理。
- **根因**：进程在终态落盘之前被中断，claim 所有者无法走完正常释放。
- **解决**：终态 JSONL 追加并 `fsync` 后才释放 claim；人工恢复时先确认进程已退出，再将遗留锁可逆改名为 `.manual-stale-<run>`，不直接删除。
- **防复发**：claim 元数据固定保存 worker-id、PID、开始时间和样本签名；启动器协调两子进程的 SIGINT。

### 3.7 旧 success 覆盖当次 partial

- **现象**：同一样本历史上有 12/12，当次严格 QC 拒绝后，Bridge 仍读到旧 success。
- **根因**：过去先筛 success，没有先按时间和来源选择最新终态。
- **解决**：先对每个 `relative_path` 取最新终态，再判定资格；手工 override 作为独立、可追溯的最新记录。
- **Git 检查点**：`000085d1`。

### 3.8 严格 QC 误拒和人工放行

- **现象**：正常 EXIF 方向图或可用普通照片被初筛到待复核。
- **根因**：用于上线正式检测的严格门禁与“评分建模希望保留更广分布”存在目标差异。
- **解决**：严格门禁不改；拒绝图复制到 `_review/补测图片人工审核_20260827`，按人脸、姿态裁切、光照曝光、模糊、遮挡有效域分类；人工决定写入 override JSONL。
- **当前决策**：人工确认 12 张放行，4 张保持拒绝；6 张 EXIF 方向修正样本全部保留。
- **防复发**：禁止按文件名硬编码；保留严格和宽松两个 Git 检查点，正式批跑固定严格版。

### 3.9 单模块空检测或算法级 partial

- **现象**：某分区有效面积为 0，或痤疮等单项因 Mask 覆盖异常失败，其他 11 项仍有完整证据。
- **风险**：整张排除会浪费其他模块；写0会污染分布。
- **解决**：有效模块继续入组，空模块记 `null` 和 `scope_unavailable_reason`；非整图 REJECT 的 `partial_success` 允许进入 Bridge。
- **Git 检查点**：`d78c0352`、`787231c5`。

### 3.10 皱纹空分区导致正式图重复

- **现象**：空分区时多个皱纹正式角色输出相同内容，触发 `DuplicateFormalImageError`。
- **根因**：“展示边界”和“可评估检测域”混用。
- **解决**：保留名义分区边界供展示，但量化选区只包含可评估区域；不可评估模块输出空状态而非伪造正常图。
- **Git 检查点**：`942420a7`、`d78c0352`。

### 3.11 服务长跑资源累积

- **现象**：长跑后 RSS、显存和 WSL 页缓存逐步升高。
- **解决**：本机默认每 slot 每 8 张受控重启常驻服务，或资源门禁提前触发回收。
- **验证**：健康 JSON 记录 `restart_count`、available memory、swap 和当前进程 RSS；本次第一轮两 slot 均成功回收。

### 3.12 进度条仍显示“九项检测”

- **现象**：十二项 consumer 运行时终端标签仍是历史“九项检测”。
- **影响**：仅是 CLI 展示误导；状态中 `success_items=12`，实际运行和输出为十二项。
- **解决计划**：进度文案改由 batch runtime 合同提供，按 profile 显示“十二项检测”，不影响对外 JSON。

### 3.13 回收周期内显存累积

- **现象**：`recycle-every=15` 的 r9 在第5轮生命周期内升至 15147 MiB/16311 MiB，只剩约 0.9 GiB。
- **排查**：进程树仅有当前 2 slot × 3 resident worker，没有旧服务僵尸；因此不是多启服务。
- **根因证据**：安全退出 r9 后显存从 15147 MiB 立即降为 0 MiB，证明累积位于当前服务生命周期。
- **解决**：r10 改为每 slot 8 张回收；两 slot 首轮回收后，GPU 忙时显存约 11811 MiB，留出约 4.5 GiB。
- **防复发**：`resource_guard.py` 需增加 GPU 余量观测和提前回收原因；在本机完成长跑验证前，不恢复15张周期。

## 4. 目标模块化结构

保留 `run.py` 作为唯一本地点火入口，最终只负责：

1. 解析 CLI 和 Settings。
2. 组装已解析的批跑配置。
3. 调用 `batch_runtime.run_batch(...)`。
4. 将结果转为进程退出码。

新目录固定为：

```text
src/nine_analysis/batch_runtime/
├── __init__.py
├── contracts.py       # BatchRunConfig、SampleSignature、TerminalState
├── manifest.py        # 只读冻结manifest，复用现有input_manifest
├── claims.py          # claim获取、心跳、终态后释放、遗留锁审计
├── state_store.py     # JSONL append+fsync、最新终态、历史失败跳过
├── input_staging.py   # NFS/本地图单图暂存、大小与JPEG完整性
├── resource_guard.py  # GPU租约、内存/Swap门禁、周期回收
├── qc_review.py       # REJECT分类归档和人工override
├── output_store.py    # /dev/shm现场、D盘单写者发布、输出Profile
├── worker_slot.py     # 单slot处理循环、超时、失败分类、健康JSON
├── launcher.py        # A/B两slot协调启动和SIGINT/SIGTERM
└── monitoring.py      # 唯一成功数、吞吐、资源和拒绝分布
```

现有文件的处理方式：

- `batch_runtime_safety.py` 的内存快照、GPU 租约和导出锁迁入 `resource_guard.py`，先保留兼容导入。
- `batch_slot_launcher.py` 迁入 `launcher.py`，命令行行为和退出码零漂移。
- `input_manifest.py` 迁入 `manifest.py`，继续使用 Pydantic 严格解析。
- `run.py` 内的 `WorkClaim`、状态读写、QC 归档和输入暂存按上述边界逐个迁出。

## 5. 实施顺序（禁止大爆炸式重构）

1. **合同先行**：为当前 `run.py` 的 manifest、claim、终态、暂存、QC、两 slot 和退出码写回归测试。
2. **纯数据结构**：先引入 `BatchRunConfig` 和 `TerminalState`，不改执行路径。
3. **输入与状态**：迁出 manifest、staging、claim 和 state store，每迁一个模块就跑专项测试。
4. **资源与输出**：迁出 GPU/内存门禁、D盘发布和 QC 归档。
5. **slot 协调**：最后迁出单 slot 循环和 A/B 启动器，减少一次性破坏断点语义的风险。
6. **清理兼容导入**：所有回归和真实 20/100 张门通过后，再删除旧壳；不在一次提交中同时移动全部逻辑。

每一步单独 Git 提交，可以独立 revert。

## 6. 必须保持的对外行为

- `run.py` 命令行字段和默认值不变。
- 默认 `capture_profile=consumer`，默认不生成 Word，其他正式结果保存。
- consumer 不调用厂家 sidecar，institution 仍显式路由。
- 本地十二项结果、CSV/JSON、回执和目录布局不变。
- Worker 公开任务参数、信封字段、Queue、Task 和 `meta_data.version="1"` 不变。
- claim 只在终态 `fsync` 后释放，同一签名只有一个正式终态。
- 评分空值、整图 QC 拒绝和算法级 partial 按第2节处理。

## 7. 模块化验收门

### 7.1 非 GPU 自动门

- manifest 模式证明目录递归枚举调用数为 0。
- NFS 短读、缺 EOI、大小/mtime 漂移测试。
- 两 slot 争抢同一签名只有一个 success。
- 终态写入并 `fsync` 前不释放 claim。
- SIGINT/SIGTERM 安全落盘，协调退出码稳定。
- 内存、Swap、周期回收和第三 slot 失败关闭。
- 整图 REJECT 排除，算法级 partial 按模块保留，空值不写0。
- QC 归档分类、人工 override 和最新终态优先级。
- 公开 Worker 字段和 consumer/institution 路由回归零漂移。

### 7.2 GPU 分级门

1. 20 张 review 烟测：结果图、十二项、QC 和输出布局。
2. 100 张 A/B 双 slot：无重复、无 OOM、无 Swap 累积、回收计数正常。
3. 200 张稳定性：无状态损坏、无重复终态、无 D 盘长时间满载。
4. 1000 张评分：可评估模块数、拒绝率、空值率、耗时和 Bridge 诊断完整。其中800张为映射拟合组，200张为独立验证组，不是检测模型训练/测试。

## 8. 标准运行参数

评分全产物（不生成 Word）的核心参数：

```bash
python run.py \
  --input-dir <冻结输入根目录> \
  --input-manifest <冻结manifest.jsonl> \
  --output-dir <新任务输出目录> \
  --job-name <唯一任务名> \
  --worker-id <唯一节点名> \
  --capture-profile consumer \
  --output-profile review \
  --no-generate-medical-report \
  --retain-scoring-artifacts \
  --runtime-dir /dev/shm/aisia-twelve-runtime/<任务名> \
  --slots 2 \
  --allow-shared-gpu \
  --skip-recorded-failures \
  --recycle-every 8 \
  --image-timeout-seconds 1800 \
  --min-available-memory-gib 16 \
  --min-runtime-available-memory-gib 4 \
  --max-swap-gib 6
```

运行前必须使用新 job-name 和新输出目录，不得与旧九项断点混写。
