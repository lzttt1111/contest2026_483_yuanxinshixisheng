## 4. 存储形式建议：inline vs 文件引用

预算参考：单算法 inline ≤512KB、单报告合计 ≤4MB、SummaryRequest 消息 ≤8MB。

| 口径 | 实测/估算 | 占 512KB | 占 4MB | 占 8MB |
|---|---:|---:|---:|---:|
| 单算法上限（wrinkle/紫区最大估算 ~10KB） | ~1.1KB（实测） / ~10KB（估算） | <2% | <0.3% | |
| 单报告 11 算法合计 | ~8.2KB（实测下限）/ ~48–55KB（估算） | — | ~1.4% | |
| SummaryRequest（含 11 算法 scoring_input + 评分输出） | 估算 <100KB | — | — | ~1.2% |

**推荐：全部 inline（`raw_result.scoring_input` 内嵌）**，阈值依据：

1. 全额证据最坏估算 ~75KB ≪ 512KB 单算法上限的 15%，无需文件引用分摊。
2. 单报告合计 ≪ 4MB；SummaryRequest ≪ 8MB。inline 使聚合侧与后端不再处理 OSS/对象存储引用与一致性（引用失效、清理误删、权限），与本次“在清理中间文件前生成、随信封持久化到 PG”的目标最契合。
3. PG JSONB 单行：完整信封（含 scoring_input）估算 <150KB，远低于 TOAST 压缩需求上限；无单行超限风险。
4. 若未来某算法证据膨胀到 >256KB，再对该算法单独切文件引用即可——阈值建议定在**单算法 256KB 或单报告 2MB**（预算的 50%），作为触发引用的告警线。

> 修正说明：本方案沿用给定预算，无需上调；实测显示余量三个数量级，保持预算即可。

## 5. ScoringInput 头部字段与 evidence 形状提案

### 5.1 头部字段

```json
{
  "schema_version": "scoring_input_v1",
  "algorithm_name": "redness",
  "detection_schema_version": "2",
  "detection_impl_version": "1",
  "report_id": "…",
  "detection_attempt_id": "…",
  "source_image_sha256": "…",
  "capture_profile": "institution",
  "input_route": "institution_vendor_rgb",
  "evidence_status": "present | partial | missing | failed",
  "quality": {
    "algorithm_quality_status": "PASS|WARNING|REJECT",
    "algorithm_quality_flags": [],
    "input_quality": null
  }
}
```

- `evidence_status`：`present`（该算法全部必需字段在场）/`partial`（部分缺失）/`missing`（未检测）/`failed`（检测失败）。聚合门禁据此拒绝把 missing 当 0。
- `quality`：区分“算法输入质量”与“原图派生门禁”。云端普通检测无 `input_quality_gate`，标记 `null`，V0.1.1 只能 REVIEW，不伪造。
- 头部字段全部可由 worker 在生成点获得；`source_image_sha256` 用于跨报告去重与追溯。

### 5.2 evidence 形状：**镜像 detector_results 子集**（推荐）

```json
"evidence": {
  "redness": {
    "metrics": { …仅消费字段… }
  }
}
```

理由：

1. 聚合侧可直接 `dict.update` 各算法 evidence 重建 `detector_results`，无需路径解析/重组，天然与 `_pool`（`v2_proxy_projection.py:91-102`）、`extract_*`（`word_*_2d.py`）的读取结构一致。
2. 与 registry 的 `source_metric_ids`（`detector.relpath`）保持同一寻址语系，覆盖校验只需剥去 `metrics.` 前缀。
3. 扁平 `path→value` 需要额外编码方括号索引与中文键，且与 `detector_results` 双向往返易错；文件级 diff/审查也不如嵌套直观。
4. 唯一次优：嵌套结构对“字段级缺失”的定位不如扁平表明确。提案用 `evidence_status` + 每字段 `null` 显式占位补足，而非静默省略。

### 5.3 evidence 强类型化

**建议：通用 `dict` + 外部冻结字段清单 + SHA 钉，不逐算法 pydantic。**

| 方案 | 代价 |
|---|---|
| 逐算法 pydantic | 需要为 11 算法 × 两 Profile 维护嵌套模型（含中文键），与 detector_results 的“算法内部结果保持不变”原则冲突；新增字段即需改契约再发版 |
| 通用 dict + 字段清单（推荐） | 契约只定义 ScoringInputV1 容器；字段清单由 registry SHA（137 公式 + `word_population_reference_1000.json` SHA）钉住，校验只做“提案字段 ⊆ evidence”覆盖检查；灵活、低维护 |

门禁必须放在聚合入口（而非仅在生成端）：`word_acne_2d.py:33-34 _number` 与 `word_wrinkle_2d.py:34-35 _number` 对非数值返回 `0.0`，若 evidence 静默缺失会把缺值当 0。聚合入口应先按 `evidence_status` 与字段清单做完整性检查，再进评分。
